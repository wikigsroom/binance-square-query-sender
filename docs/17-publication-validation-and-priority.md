## 查到的实际原因

服务、数据库和 Worker 正常，失败发生在模型成稿之后、上传与发布之前。不同任务遭遇了以下校验问题：

| 问题 | 实际例子 |
| --- | --- |
| `TOKEN_TAGS` | 正文写了 BTC、ETH，但没有对应的 `$BTC`、`$ETH` 标签 |
| `NEWS_EVIDENCE` | Kalshi/BitGo 新闻的证据挂到了 MASK 新闻的快照编号；另有证据原句被模型改写 |
| `NEWS_DATE` / `NEWS_PROGRESS` | 报道日期未按校验格式出现，或进展措辞未通过规则检查 |
| 语义与同质化审稿 | 结尾与历史稿件采用相似的谨慎判断结构 |

最初手动任务 `job_4e9f3e77-8060-4f08-944f-0326c865276d` 连续三次成稿被拒绝，没有发布意图或远端提交。自动任务也出现相同类别的问题。

程序另有两处缺陷：返修仅携带上一稿正文，未携带标签与新闻证据元数据；历史取材包含已经被拒绝的草稿，增加了后续稿件被判同质化的概率。现已补全结构化返修输入，历史范围限定为实际发布内容及正在准备提交的已通过成稿。

## 发送优先的行为

- 不调用 AI 语义审稿，不因文风、翻译腔、同质化或观点质量要求返修。
- 禁词、标签、币种元数据、涨跌幅、新闻编号、证据片段、日期和进展等内容问题均记录为 `warnings`，不作为发布错误。
- 内容新鲜度检查记录提示；提交前不因素材等待造成的快照过期而反复重写。
- 保留非空正文、预设长度上限、AI 输出与成稿摘要一致性、批准模型证据、图片来源和可读取性、账号与接口状态、执行租约及避免重复提交的检查。
- 正文仍由现有 `gpt-6-luna` 接入生成；配图继续按账号当前预设使用 `gpt-image-2.5` 新生图。未将正文改为程序拼接或固定模板。

校验记录携带 `validationMode`。内容问题可在任务详情的校验提示中查看，历史失败记录保留。每轮校验立即关联到任务，旧任务则通过其错误记录中的 `validationId` 读取，任务详情同时返回 `validationHistory`。
